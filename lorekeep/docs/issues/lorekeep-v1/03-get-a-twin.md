# 03: `get` stores a Twin as a Version

**What to build:** A worker runs `get <url>` for a page whose host rule names a Twin and receives the path of a Version `<host>--<path>--<sha8>.md` with frontmatter `url` (normalised, after redirects and `canonicalUrl`, Twin suffix removed and `page_suffix` restored), `fetched_at`, `sha256`, `publisher`, `authority`, `converter: md-twin`, `etag`/`last_modified` when served, `title`, `modified` (first present of `ms.date`, `updated_at`, `lastmod`, `date` in the Twin's frontmatter), `original {url, mediatype, sha256, stored: false}` where `original.url` is the Twin address the bytes came from and `original.sha256` hashes them. The Twin's own frontmatter is stripped from the body, which is otherwise as published, links included. When the normalised address asked for differs from `url`, an `aliases.csv` row is committed, also when the Version already existed. A Twin is accepted only when the response is `text/markdown`, or `text/plain` under a `raw` rule; otherwise the response is discarded, `get` reports that no Twin was found and, in this ticket, exits non-zero (ticket 04 then fetches the page URL instead). Before any request, `get` uses ticket 02's lookup and, when a Version exists, returns it without fetching and appends the Run's Tag if missing. The address sent is the one given (or the Twin address the rule builds from it), never the normalised one. The cascade is an ordered list of steps that 04–06 extend; every write goes through ticket 02's commit function. Every request carries a `User-Agent` starting with `lorekeep/`.

## Comments

2026-10-17 — Decisions made while building this ticket. (1) Layout: `lorekeep.http` builds the one client (`make_client(transport)`: redirects followed, `User-Agent: lorekeep/<version>`) and reads a response's media type; `lorekeep.cascade` holds `STEPS` and `run_cascade`, with `Request`, `Fetched`, `Fallthrough` and the `Step` protocol in `cascade/step.py` and the Twin step in `cascade/twin.py`. Tickets 04–06 append their steps to `STEPS`; `run_cascade` returns the first `Fetched` or every step's `Fallthrough`, and `get` exits 1 with `nothing stored for <url>: <reasons>` (here: `no Twin: <address> answered text/html`). `commands/get.py` builds the frontmatter from `Fetched` and commits Version, Tag row and alias row in one call. (2) Twin addresses: `md-suffix` drops a trailing slash, replaces `page_suffix` or appends `.md`; an address already ending in `.md`, or already carrying `accept=text/markdown`, is sent as given. A leading `---` block that is not a YAML mapping stays in the body. `modified` is the first of the four keys whose value starts with a `YYYY-MM-DD` date. `origin: web` is written explicitly. (3) "The second call fetches once" (old address used after the canonical page is stored) is read as one pass of the cascade: the Twin address built from the old one, its two `301`s and the Twin, asserted request by request. (4) Outcomes in `--json`: a lookup hit is `fresh` (ticket 07 adds the window); a new file of a Source the Store had no Version of is `stored`. Revised 2026-10-17 (review fix A2): when the cascade ran because the address was new but the Source already has a latest Version (an alias not yet known, a canonical address), that fetch is a Recheck and is recorded as one in `checks.csv` with status `200` — equal Markdown hash is `unchanged`, a different one is a new Version beside the old and a `changed` row — so the lookup names the Version current after the call instead of the one an older row named. (5) The unknown-host warning is printed on every `get` of such a host, lookup hits included.
