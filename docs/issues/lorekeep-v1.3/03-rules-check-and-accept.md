# 03: a subagent proposes rules, `lorekeep rules check` measures, `rules accept` writes

**What to build:** No model inside lorekeep and no API key (owner, 2026-10-17: the tool already runs in an agentic flow). Three parts. (1) `lorekeep rules sample PREFIX [--sample N]` prints the paths of up to N Versions under the prefix (default 5: the shortest, the longest, three between) — the material for a proposer. (2) `lorekeep rules check FILE [--store DIR]` reads candidate `[[readings]]` rules from a TOML file, applies each to every Version under its prefix, and prints per candidate: lines removed or headings inserted (total; min, median, max per Version), three removed lines as examples, and `pass` or `fail` with the reason against the limits (at most 30% of a Version's lines; never a fence or a pipe-table line; `drop_leading` only before the first heading); writes nothing. (3) `lorekeep rules accept FILE` runs the same check and appends the passing rules to the Store's `lorekeep.toml` with `accepted` (today) and `removes` (the measured share), then rebuilds the Readings under their prefixes; `--all` also accepts the failing ones (owner's override). (4) `references/owner.md` gives the orchestrator the brief for the proposer: launch a subagent on the cheapest model available (the Haiku tier, through Orca orchestration as any worker), hand it the sampled paths and the rule grammar, and require the answer as one TOML file of `[[readings]]` candidates, nothing else; then `rules check`, read the report, `rules accept`. The engine defaults in `src/lorekeep/readings.toml` come from running that cycle live on the first Store. Decisions: `spec.md` › Rules proposed by a subagent.
